調査対象: 設計書「設計書/バリデーション定義.txt」およびソース「app.js」

1. 設計書上の要件
- 販売画面 (T_販売) のバリデーションにて「発送方法」は必須。
- 「送料合計」は任意。
- 発送方法選択時には、該当発送方法名と一致する梱包材在庫を確認する業務チェックがある。

2. app.js の現状確認
- app.js の validateData() に定義されている T_販売 のルールは以下。
  ・date: required: true
  ・buyer: required: true
  ・item: required: true
  ・quantity: required: true, min: 1
  ・price: required: true, min: 0
  ・shipping: required: true
  ・shippingCost: required: false, min: 0
- この時点で、設計書の「発送方法必須」「送料合計任意」と整合している。

3. 追加業務バリデーションとの整合性
- app.js では販売登録時に以下を確認している。
  ・商品在庫が数量分存在するか（個人用の新規品名はスキップ）
  ・発送方法が選択されている場合、T_在庫集計 に同名の梱包材在庫があるか
- これも設計書の業務バリデーション要件と一致している。

4. 既存コードへの影響とデグレ観点
- 上記整合性を維持する限り、販売登録の入力バリデーションが強化されるだけであり、他画面や他シート処理への影響は限定的。
- ただし、販売タブの既存未入力ケースで発送方法を空にした状態で送信可能だった場合、今回の設計反映によりそのケースは弾かれる。
  つまり、意図的な仕様変更ではあるが、設計要件に沿った正常化でありデグレとは言えない。
- なお、本調査では backend.gs や index.html の別処理の完全網羅は行っていないため、ソース全体の副作用までは確認できていない。

5. 結論
- 設計書の要件に対して、app.js の販売バリデーション実装は整合している。
- 現在の該当コードでは「発送方法必須」「送料合計任意」「梱包材在庫チェック」の設計要件を満たしている。

6. 追加設計書との整合性確認
6.1 スキーマ定義
- `設計書/スキーマ定義.txt` の `T_販売` では、`発送方法(F列)`、`送料(G列)`、`送料負担区分(P列)` が明記されている。
- app.js では `sale-shipping`/`sale-shipping-cost`/`sale-shipping-payer` を正しく扱い、`registerTransaction` は `発送方法` と `送料` を `T_販売` にマッピングしているため、スキーマ側と整合している。

6.2 プルダウン・マスタ制御定義
- `設計書/プルダウン・マスタ制御定義.txt` の販売タブでは、`sale-buyer` が `M_売先`、`sale-item` が `M_商品`、`sale-shipping` が `M_発送` を参照する。
- app.js は `sale-buyer`, `sale-item`, `sale-shipping` の各要素IDを使っており、`sale-item` は `suggest-strict` のマスタチェックも行っているため、画面制御側との整合性も問題ない。

6.3 マスタ編集画面定義
- `設計書/マスタ編集画面定義.txt` の `M_発送（配送方法）` では `発送方法` が編集キー、`送料` が数値入力として定義されている。
- app.js では `sale-shipping` 選択時に `M_発送` の `送料` を `sale-shipping-cost` に自動セットするロジックがあり、マスタ編集仕様と整合している。

6.4 運用ルール
- `設計書/運用ルール.txt` の販売ルールでは、販売ステータスと日付の自動補完などが定義されている。
- 本調査対象の app.js での販売登録時バリデーションとは直接重ならないが、ステータスマッピングや販売日時の扱いは `T_販売` のスキーマ設計と矛盾していない。

6.5 処理ルール一覧
- `設計書/処理ルール一覧.txt` の販売アクションでは、販売登録時に `販売ID, 売先, 品名, 数量, 価格, 発送方法, 送料, 手数料, 合計単価, ステータス, 販売開始日` を記録するとある。
- backend.gs の `registerTransaction` はこれらをほぼ満たしており、特に `M_売先` の手数料率に基づく `commission` 計算も実装されている。
- ただし `registerTransaction` のマッピング定義では現時点で `価格`, `送料`, `送料負担区分`, `手数料`, `管理区分` を扱うが、`合計単価` は `data.price / quantity` による簡易計算で設定されるため、処理ルール一部の文言と実装が微妙に異なる可能性がある。

6.6 履歴表示仕様
- `設計書/履歴表示仕様.txt` は販売履歴カードに `送料` を表示することを求めている。
- app.js の履歴描画部には `送料:¥${(item['送料'] || 0).toLocaleString()}` 表示が存在しており、仕様と整合している。

6.7 内部設計書間の不整合
- ただし、`設計書/バリデーション定義.txt` では `送料合計` が「任意」になっている一方、`設計書/バリデーション実装定義書.md` では修正後に `送料合計` の必須表記が解除され、`任意` と一致している。
- これにより、設計書同士の `送料合計` の必須/任意要件の不一致は解消された。

7. まとめ
- 仕様・画面定義・マスタ制御・履歴表示の観点では、app.js と backend.gs の実装は大筋で整合している。
- ただし、設計書内に `送料合計` の必須性に関する文書間矛盾があるため、これを揃える必要がある。
- 今回の調査では、コード変更は行っていない。
